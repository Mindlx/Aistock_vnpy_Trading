# c1skill for Goose

> 改编自 `~/.agents/skills/c1skill/SKILL.md`（原 c1skill 方法论）
> 适配 Goose 的工具能力（shell/rg/analyze/tree/git log）

---

## 概述

c1skill 是一套**交叉层问题审计与修复方法论**，对多层系统中发现的任何问题，执行从原架构理解 → 跨维度证据论证 → 修复 → 验证的完整闭环。

**适用场景**：多层系统（融合系统/三子系统）中的数据一致性、信号冲突、架构矛盾问题。

**不适用场景**：简单的 bug 修复、配置修改、日常编码——这些按正常流程即可。

---

## 8 阶段闭环

### Stage 0 — 原架构理解（最重要）

在定义任何问题之前，先理解设计意图。

**Goose 工具**：
| 工具 | 用途 |
|:----|:-----|
| `shell rg` | 搜索代码中的注释、docstring、设计文档引用 |
| `shell git log` | 追溯提交历史、原始设计意图 |
| `analyze path` | 查看代码结构、函数/类定义 |
| `tree` | 浏览目录结构 |

**产出**：原架构设计意图摘要（≤ 1 段话）+ "刻意 vs 偶然"判定

---

### Stage 1 — 精确定义问题

在 Stage 0 完成的基础上，精确定义问题。

**产出**：
- 问题描述（1 段话）
- 严重程度（CRITICAL / HIGH / MEDIUM / LOW）
- 影响范围（哪些下游链路受影响）
- 与原架构的关系

---

### Stage 2 — L2 证据搜集（并行）

利用 Goose 的并行工具能力，同时从多维度搜集证据。

**证据维度矩阵**：

| 维度 | L2 来源 | Goose 工具 |
|:----|:--------|:----------|
| **代码逻辑** | 源码、函数定义、数据流 | `analyze` + `rg` |
| **文档意图** | 架构文档、ADR、设计文档 | `cat` + `rg` |
| **Git 历史** | 提交信息、变更记录 | `git log --all` |
| **运行时数据** | 数据库、配置文件、日志 | `python3 -c sqlite3` + `cat` |
| **测试验证** | 测试用例、跑测结果 | `pytest` + `shell` |

---

### Stage 3 — 综合判断

将所有证据按"支持 / 反对"问题成立分类。

**产出**：判决矩阵

| 维度 | 支持 | 反对 | 最强单一证据 |
|:----|:---:|:---:|:------------|
| 代码逻辑 | | | |
| 文档意图 | | | |
| Git 历史 | | | |
| 运行时数据 | | | |
| 测试验证 | | | |

---

### Stage 4 — 主动寻找反方论据

**关键步骤**。假设原论述是错误的，主动寻找反方证据。

**Goose 工具**：
- `shell git log --all --oneline -20` — 看是否有你明确拒绝这种做法的记录
- `rg "FIXME\|TODO\|HACK\|XXX"` — 看代码中是否有相关警示
- `rg -- docs/decisions/` — 看是否有相关的 ADR 反驳

---

### Stage 5 — 修复方案设计

**分级方案**：

| Phase | 类型 | 说明 | 示例 |
|:-----|:----|:-----|:-----|
| **P1** | 零风险改动 | 文档/配置/prompt 注入，立即生效 | 改 `.goosehints` |
| **P2** | 经验诊断脚本 | 测量实际参数，验证假设 | 写诊断脚本看数据 |
| **P3** | 条件逻辑改动 | 需 P2 数据支撑，否则跳过 | 改权重 / 改回测口径 |

**产出**：逐 Phase 方案 + 工作量估算 + 什么情况下跳过

---

### Stage 6 — 实施与验证

**实施后验证**：
1. 编译/语法检查：`python -m py_compile`
2. 跑测试：`pytest tests/`
3. 对比输出：改之前的差异
4. 如果 P2 涉及经验测量，记录实际数据与假设的偏差

---

### Stage 7 — 自我批判

回到 Stage 0 的发现，判断修复是**增强还是违背**了架构初衷。

- 如果是增强 → 标注"补全了原始设计的缺失环节"
- 如果是违背 → **不要修复**。标注为"设计意图如此，非问题"

---

## 触发指令

当我说以下语句时，你应按 c1skill 流程执行：

| 触发语 | 说明 |
|:------|:-----|
| "用 c1skill 分析 X" | 完整 8 阶段 |
| "c1skill 快速分析 X" | Stage 0 → Stage 1 → Stage 5（跳过完整证据搜集）|
| "c1skill 验证 X" | Stage 4 + Stage 6（反方验证 + 实施验证）|

---

## 与普通工作方式的区别

| 维度 | 普通方式 | c1skill 方式 |
|:----|:--------|:------------|
| 修改前 | 看你交代的规则 | 强制 Stage 0：追溯原架构设计意图 |
| 证据 | 以代码为准 | 多维度并行（代码+文档+git+数据+测试）|
| 反方 | 不强制 | 强制 Stage 4 主动找反方证据 |
| 方案 | 一步到位 | 分级（P1 零风险 → P2 诊断 → P3 逻辑改动）|
| 验证 | commit 前检查 | 全流程验证 + Stage 7 自我批判 |
