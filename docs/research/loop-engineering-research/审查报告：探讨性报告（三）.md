## 一、总体评价

本报告是一份**技术细节充分、路线清晰**的模型微调实施方案。从数据采集、清洗转换、LoRA+DPO 训练到评估部署，整条链路各环节都有具体参数和代码框架，在同类方案文档中属于上乘。

然而，**方案建立在一个未经验证的核心假设之上**：即 Oracle 初始推荐与 c1skill 最终结论构成有效的 DPO 偏好对。这个假设决定了整个方案的可行性——如果它不成立，数据采集、清洗、训练的全部设计都需要重新审视。

**综合评分**: 7.2/10

### 第三节：数据采集方案（核心审查对象）

这是整份方案最关键也最薄弱的部分。三个问题：

#### 问题 C1：采集脚本的实现难度被严重低估

报告中展示的 `data_collector.py` 框架代码（附录 A）是**伪代码**——`extract_requirement()`、`extract_oracle()`、`extract_c1skill()` 等函数体为空，标注了"具体解析逻辑需根据实际日志格式定制"。这恰恰是整个方案中最困难的部分：

| 函数 | 实际难度 | 原因 |
|------|---------|------|
| `extract_requirement()` | 🔴 高 | Sisyphus 与用户的对话是自然语言多轮交互，不是结构化的 JSON 输入。提取"最终明确的需求描述"需要 NER + 摘要，不能用正则解析 |
| `extract_oracle()` | 🟡 中 | Oracle 输出有一定结构（Markdown 格式），但并非一致的 JSON schema，需要按段落模式解析 |
| `extract_c1skill()` | 🔴 高 | c1skill 的输出格式因问题类型而异。辩论记录、攻击/防守对、负面评分等字段不是标准化输出的 |
| `extract_lsp()` | 🟢 低 | LSP 诊断本身是结构化的（文件/行/列/消息），解析难度最低 |

**结论**: 数据采集脚本的开发工作量被低估了至少 5-10 倍。⚠️

#### 问题 C2（核心假设）：Oracle 初始推荐 ≠ "坏的答案"

方案的核心逻辑是 `chosen = c1skill.final_conclusion`、`rejected = oracle.initial_recommendation`。这个假设**成立的前提是：c1skill 的论证总是优于 Oracle 的初始推荐**。

但这个前提存在结构性风险：

**风险 A：Oracle 与 c1skill 不是"初版 vs 修改版"的关系**
- Oracle 是**一种审慎的、只读的深度分析 Agent**，其输出已经是经过深思熟虑的论证
- c1skill 是对 Oracle 的论证进行**对抗性质疑和压力测试**，并非"修改错误"
- 在大多数情况下，c1skill 的最终结论与 Oracle 的初始推荐**高度一致**——c1skill 的辩论环节确认了 Oracle 的方向，而不是推翻它
- 如果两者高度一致，则 `chosen` 和 `rejected` 非常相似，DPO 优化信号极弱甚至为零

**风险 B：c1skill 也可能犯错**
- c1skill 的反方博弈环节可能引入**过度的怀疑**，导致原本正确的方案被不必要地复杂化
- 有些场景下 Oracle 的方案更优，c1skill 的过度辩解反而降低了质量
- 这种情况下，`rejected` 实际上优于 `chosen`，DPO 训练会向错误方向优化

**风险 C：缺少质量标签就无法区分**
- 如风险 B 所述，并非所有 c1skill 结论都优于 Oracle 推荐
- 方案依赖用户评分（≥4 分）来筛选，但用户评分是**主观且稀疏的**
- 如果没有每条轨迹的"哪个方案更好"的标注，DPO 训练信号充满噪声

**建议**: 将偏好对改为**人工标注的"好 vs 差"方案**，而非自动假设 Oracle < c1skill。或者在数据累积足够后，通过事后回测客观验证哪个方案在市场预测中更准确。

#### 问题 C3：数据量估计过于乐观

| 项目 | 报告估计 | 更现实的估计 | 说明 |
|------|---------|-------------|------|
| 每月 Ultrawork 运行 | 假设每天 1-2 次 | 实际 C1 级复杂任务约每周 3-5 次 | 不是所有工作都触发完整流程 |
| 30-60 条/月 | 第 1-4 周积累 | 更现实：第 1-4 周积累 15-30 条 | 高频任务不需要 Oracle+c1skill |
| DPO 所需数据量 | 未讨论 | 同类项目经验：至少 500-1000 偏好对 | 30-60 条训练 27B 模型严重不足 |
| 经过滤后的有效数据 | 假设 100% 可用 | 质量过滤 + 评分门槛后约 50% 留存 | 15-30 条有效样本 |

**建议**: 增加数据增强策略（如将每条轨迹切分为多个偏好子问题），或降低期待——先用这个方案在 7B 模型上验证流程，再扩展到 27B。

### 第四节：微调实施方案

这一节是整份报告中技术最为扎实的部分。

| 维度 | 评价 |
|------|------|
| LoRA+DPO 路线 | ✅ 合理的选择。DPO 避免了复杂的 PPO 训练 |
| 基座模型选择 | ✅ Qwen3.6-27B 是合理的起点 |
| 显存估算 | ✅ ~22GB/卡，留在 24GB 上限内，有安全余量 |
| 训练参数 | ✅ 参数选择合理（r=16, lr=5e-6, batch=2） |
| 训练时长 | ✅ 60-90 分钟，符合预期 |

**问题 D1**: 4-bit 量化加载 Qwen3.6-27B 后，LoRA 训练的有效性如何？量化引入的信息损失可能限制 LoRA 的表达能力——低秩适配在低精度基座上的效果尚未被充分验证。

**问题 D2**: 附录 B 的 `FastLanguageModel.from_pretrained` 中 `dtype=None` 会自动高精度加载某些层，可能增加意外的显存开销。

**建议**: 先在一个更小的模型上（Qwen2.5-7B）跑通完整流程验证，再扩展到 27B。

## 四、本报告未涉及的内容（补充说明）

以下内容在报告中未讨论，但对方案可行性有重大影响：

### 4.1 增量训练策略

当前方案假设"一次性积累 30-60 条 → 训练一次"。但没有讨论：
- 当数据积累到 100 条、200 条时是否需要重训？
- 每次重训是覆盖还是合并旧权重？
- 如果模型已经学到的模式被新数据覆盖（灾难性遗忘），如何缓解？

**建议**: 引入持续学习（Continual Learning）策略，如 Elastic Weight Consolidation（EWC）。

### 4.2 回退机制

如果微调模型上线后表现不佳，如何在不中断生产的前提下快速切换回 DeepSeek API？当前方案缺少：
- 特征开关（Feature Flag）——按任务类型/股票代码/复杂度分流
- A/B 测试框架——部分流量走微调模型，部分走 API，对比效果
- 一键回滚——模型权重出错时如何快速恢复

**建议**: 增加模型推理的 fallback 链：微调模型 → DeepSeek Flash → DeepSeek Pro。

### 4.3 Token 成本节省的量化分析

报告的目标之一是"节约 LLM Token 花费"，但全文没有对 Token 消耗进行任何测算：
- 当前每天/每周的 API Token 消耗是多少？
- 微调模型替代的是哪些调用场景？覆盖多少 Token 量？
- LoRA 训练本身需要 GPU 电力成本（双卡 3090 满载约 700W）
- 投资回报期是多长？

**建议**: 增加一个简单的 ROI 分析表。

### 4.4 与当前系统的集成点

方案说"在 Sisyphus Ultrawork 完成回调中注入数据采集钩子"，但：
- 当前是否有"完成回调"机制？OpenCode 是否支持 post-execution hook？
- 数据采集钩子由谁触发——Sisyphus 自己、外部 cron、还是手动？
- 采集钩子执行失败是否影响主流程？

**建议**: 将这些集成问题转为明确的"是/否"检查清单。

### 4.5 法学伦理注意事项

- Apache 2.0 模型进行 DPO 微调后，是否需要公开 LoRA 权重？
- 训练数据包含用户的代码和决策记录，隐私边界在哪？
- 如果微调模型为公司/商业使用，是否存在合规风险？

## 六、核心结论

### 6.1 方案可行性分级

| 层级 | 可行性 | 说明 |
|------|--------|------|
| 🟢 **硬件可行** | 高 | 双卡 3090 + 4-bit + LoRA 可训练 27B |
| 🟢 **技术路线可行** | 高 | DPO + LoRA 是成熟的微调方法 |
| 🟡 **数据方案存疑** | 中 | 采集脚本开发工作量大，偏好对假设需要验证 |
| 🔴 **核心假设未经检验** | 低 | Oracle vs c1skill 作为偏好对的有效性未知 |

### 6.2 建议的先行验证步骤

在投入完整实施之前，建议先做一个小规模验证：

```
步骤 1: 手动收集 5-10 条历史 Sisyphus 运行轨迹（直接复制粘贴）
步骤 2: 为每条轨迹人工标注 "Oracle 方案" 和 "c1skill 方案" 哪个更好
步骤 3: 如果 Oracle 方案在一个显著比例（≥30%）的案例中不劣于 c1skill 方案
         → 核心假设不成立，需重新设计偏好对来源
步骤 4: 将 5-10 条数据格式化后，用 Qwen2.5-7B 跑一次微型 DPO 实验
步骤 5: 检查训练是否可以收敛（loss 是否下降）
```

这套验证实验可以在**一个周末**内完成，不需要部署数据采集钩子。

### 6.3 最终意见

**本方案在技术路线上合理，工程细节扎实，但建立在一个未验证的核心假设之上。建议先完成 6.2 节的小规模验证后再决定是否全面投入。** 如果验证结果表明 Oracle 与 c1skill 的偏好对有效，则方案的整体评分可以从 7.2/10 上调至 8.5+/10。
