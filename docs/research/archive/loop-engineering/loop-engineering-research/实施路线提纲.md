# 实施路线提纲：从推理轨迹到方法论蒸馏

> **基于**: 探讨性报告三 V2 + Oracle 战略分析 + c1skill 审查结论
> **修订说明**: 成本不纳入决策，本地训练非必须，直接使用 DeepSeek Flash
> **日期**: 2026-06-18

---

## 一、愿景：我们要实现什么

### 1.1 最终目标

将 c1skill 7 Stage 方法论固化为一套可复用的推理模板，使得**每次调用 DeepSeek Flash 时自动输出带 c1skill 论证风格的结论**，而非依赖人工在提示词中重复要求。

```
当前                        未来
────                         ────
每次手动要求                  内置 c1skill prompt 模板
"请用 c1skill 论证"           → 每次分析自带 7 Stage 结构
↓                             ↓
输出格式随 prompt 质量波动     输出格式一致，论证结构固定
论证过程不持久化               论证过程自动结构化留存
```

### 1.2 阶段效果

| 阶段 | 状态 | 效果 |
|------|------|------|
| **当前** | ad-hoc 使用 c1skill | 每次靠人脑记住要调 c1skill |
| **模板化**（第 1 周） | c1skill prompt 固化到系统提示 | 每个分析请求自动附加 c1skill 指令 |
| **轨迹结构化**（持续） | 每次推理的论证链自动提取存储 | 轨迹数据集自然积累 |
| **方法论蒸馏**（可选） | 用积累的数据集微调本地模型 | 降级场景的兜底能力提升 |

### 1.3 成功的量化标准

```
1. 日常分析中，≥ 80% 的输出自带 7 Stage 论证结构（抽样检查）
2. 每次分析后，论证链关键字段自动提取并存入轨迹库
3. 轨迹库在 30 天内累计 ≥ 50 条有效记录
4. （可选）本地模型达 DeepSeek Flash 质量的 60%+
```

## 二、路线步骤

### 第 1 步：c1skill 模板固化（本周）

将 c1skill 方法论从"人脑记忆"固化为 OpenCode 的可复用组件：

| 动作 | 产出 | 工作量 |
|------|------|--------|
| 编写 c1skill 系统提示词模板 | 一份可直接附加到任何分析请求的 prompt 段落 | 30 min |
| 注册为 OpenCode 技能或 slash command | `skill(name="c1skill")` 可调用 | 15 min |
| 验证：触发一次分析，检查输出是否包含 7 Stage 结构 | 质量检查通过 | 10 min |

**模板要点**（不需要每次走满 7 Stage，但框架一致）：
```
## 论证框架（c1skill 7 Stage）
0. 原架构理解：先说明当前系统的设计意图与约束
1. 事实声明：列出所有可验证的客观事实
2. 证据验证：深入代码/数据检查上述事实
3. 缺失分析：识别当前方案未覆盖的内容
4. 反方论据：主动提出 2-3 个对抗性观点并回应
5. 方案评估：比较各选项的优劣
6. 风险评估：明确实施风险与监控指标
7. 最终结论：输出经过全方位质疑的可执行结论
```

### 第 2 步：结构化轨迹沉淀（持续）

设计一个**零摩擦的轨迹采集机制**——核心原则：不增加额外操作负担。

现有条件：每次分析都在 OpenCode 会话中进行，会话本身已包含完整推理链。

| 层次 | 方案 | 自动化程度 |
|------|------|----------|
| **L1：会话即轨迹** | 每条分析完成后，运行命令导出为 JSON | 手动触发，零开发 |
| **L2：结构化提取** | 用 DeepSeek 提取关键字段 | LLM 辅助，半自动 |
| **L3：自动入库** | systemd timer 扫描新会话自动提取 | 全自动 |

**当前阶段**：L1 即可。每次完成分析后，运行一个命令：
```bash
python scripts/trace_collect.py --session-id ses_xxx --output data/traces/
```

单条轨迹格式（与报告三 V2 一致）：
```json
{
  "trace_id": "2026-06-19_001",
  "requirement": "用户原始需求",
  "oracle_analysis": "Oracle 分析结论",
  "c1skill_validation": {
    "stage_4_arguments": "反方论据",
    "stage_7_conclusion": "最终结论"
  },
  "final_outcome": "代码变更摘要"
}
```

### 第 3 步：轨迹数据集积累（持续至 50-100 条）

不设时间目标。每天正常使用，每次走完 c1skill 流程的任务都导出一条轨迹。

| 指标 | 目标 |
|------|------|
| 每周有效轨迹 | ≥ 3 条（任何类型任务均可） |
| 分歧率（Oracle vs c1skill） | 持续跟踪，≥ 30% 为健康 |
| 数据集总规模 | 累计至 50-100 条后评估下一步 |

### 第 4 步（可选）：模型蒸馏

当轨迹数据集达到 100+ 条时，评估是否需要对本地模型（Qwen3.6-27B）进行微调。

| 决策 | 条件 |
|------|------|
| **训练** | 分歧率持续 > 30% + 改善率 > 60% + 有明确的降级需求 |
| **不训练** | 分歧率低 / Flash 已完全满足 / 降级已有 llama.cpp 兜底 |
| **只发布数据集** | 数据集本身有价值，可开源发布 |

**核心观点**：训练不是必须的。Flash 成本极低（¥10/月），llama.cpp 已有回落兜底。数据集本身就是有独立价值的资产。

## 三、与报告三 V2 的关系

本路线沿袭报告三 V2 的目标——**将 c1skill 方法论蒸馏为可复用的能力**——但调整了路径：

| 报告三 V2 原方案 | 本路线 |
|----------------|--------|
| 目标产出：微调模型权重 | 目标产出：固化 prompt 模板 + 结构化轨迹数据集 |
| 核心动作：采集 → DPO 训练 → 评估 | 核心动作：模板固化 → 日常使用 → 轨迹沉淀 |
| 前置依赖：80+ 条轨迹 + GPU 训练 | 前置依赖：零（现有工具链即可） |
| 风险点：核心假设未验证、训练可能失败 | 风险点：几乎为零（模板随时可调，无不可回退操作） |
| 价值前提：成本节省 | 价值前提：方法论固化 + 数据资产沉淀 |
| 训练：必须依赖训练 pipeline | 训练：可选，有数据后再说 |

## 四、关键节点看板

```
□ [本周] c1skill 模板固化
    ├── prompt 模板编写完成
    ├── 注入 OpenCode 技能系统
    └── 验证一次分析输出

□ [持续] 轨迹累积
    ├── 每次 c1skill 分析后导出轨迹
    └── 每周检查分歧率

□ [50 条] 首次数据质量评估
    ├── 分歧率 ≥ 30% → 数据集健康
    └── 分歧率 < 15% → 检查模板有效性

□ [100 条] 决策点：是否训练
    ├── 有降级需求 + 数据健康 → 启动 27B 微调（约 ¥0.8 + 2h）
    ├── 仅数据资产 → 发布数据集
    └── 无需动作 → 维持现状

□ （可选）27B 训练 → 评估 → 部署
```

## 五、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| **模板固化后仍然忘记调用** | 中 | 低 | 集成到 OpenCode 默认 system prompt，每次自动附加 |
| **轨迹提取增加操作摩擦** | 中 | 低 | L1 手动导出 ≤ 1 分钟；如果仍觉得累，可以跳过——会话本身已经是轨迹 |
| **最终决定不训练** | 高 | 低 | 数据资产本身有价值。训练从来不是必须的 |
| **Flash API 涨价或不可用** | 低 | 中 | llama.cpp 容器已有回落兜底 |
| **数据集达不到 100 条** | 中 | 低 | 无需焦虑——轨迹采集不是 KPI，到不了说明日常使用密度本身就低 |
