# 探讨性报告（三）：从推理轨迹到专属模型——数据沉淀与微调实施方案\-v2



**报告性质**：基于深度对话与实证评估的课题性研究分析

**日期**：2026\-06\-18

**实证依据**：报告二的12条能力评估结论 \+ 审查报告三的技术可行性分析 \+ c1skill论证报告的核心假设检验

**关联报告**：本报告为系列第三篇，前两篇分别阐述了工作范式（报告一）与能力评估（报告二）





## 一、背景与动机



### 1\.1 当前状态



报告一描述了用户已构建的“专家决策委员会”工作范式：Sisyphus发起任务 → GitNexus/Explore全局洞察 → Oracle深度论证 → c1skill（7 Stage）验证 → LSP校验 → 安全落地。该流程的推理能力依赖DeepSeek V4 API，每日产出若干条经过完整论证的C1级问题解决方案。



报告二的实证评估确认了以下能力基线：

- Sisyphus/ulw、Oracle、GitNexus、LSP等工具链稳定运行

- `c1skill`作为7 Stage论证方法论已被沉淀并在实践中使用

- 工作流模式稳定，工程纪律（Commit不Push）严格执行

- 短板：需求队列未显式管理，质量反馈未结构化记录

    

### 1\.2 核心洞察



每一次上述流程的完整运行，都会产生一份结构完整的“推理轨迹”：

- 需求定义（直接指令或引导式对话）

- GitNexus提供的全局代码洞察

- Oracle的深度论证报告（含根因分析、方案对比、理论依据）

- `c1skill`的7 Stage论证记录（含反方论据、风险评估、最终结论）

- LSP校验结果

- 最终代码变更

    

这些轨迹目前仅服务于当次修改，随后未被结构化为可复用的数据资产。若能将其留存并用于模型微调，则可实现从“调用通用API完成工作”到“拥有一个内化了`c1skill`方法论的专业模型”的跃迁。



### 1\.3 目标



将每次运行的完整推理轨迹沉淀为训练数据，利用双卡RTX 3090工作站微调Qwen3\.6\-27B，最终产出一个**掌握了****`c1skill`****论证方法论的专属模型**，在关键环节为通用API提供补充或替代。

## 三、数据采集方案



### 3\.1 采集对象



每次Sisyphus Ultrawork完整运行结束后，从对话历史和Agent输出中提取以下结构化信息：



```JSON
{
  "trace_id": "2026-06-19_001",
  "timestamp": "2026-06-19T02:00:00Z",
  "requirement": {
    "source": "direct_instruction",
    "description": "用户原始需求描述"
  },
  "code_insight": {
    "affected_files": ["src/core/memory.c"],
    "impact_scope": "影响范围描述"
  },
  "oracle_analysis": {
    "root_cause": "根因分析结论",
    "theoretical_basis": "引用的理论与文献",
    "initial_recommendation": "Oracle初始推荐的方案"
  },
  "c1skill_validation": {
    "stage_0_arch_understanding": "原架构理解",
    "stage_4_counter_arguments": "反方论据与回应记录",
    "stage_6_risk_assessment": "风险评估结论",
    "stage_7_final_conclusion": "最终修正方案"
  },
  "lsp_diagnostics": {
    "pre_errors": [],
    "post_errors": []
  },
  "final_outcome": {
    "patch_summary": "变更摘要",
    "commit_hash": "abc1234"
  }
}
```



### 3\.2 采集方式



**过渡方案（当前阶段）** ：手动或半自动采集。由于Sisyphus的对话是自然语言交互，Oracle和`c1skill`的输出格式因问题类型而异，自动化解析的开发工作量较大。初期可先通过复制粘贴关键对话片段的方式积累前10\-20条轨迹，用于验证DPO训练的整体流程。



**长期目标**：开发自动化采集钩子，在Sisyphus每次任务完成后自动提取并结构化存储上述字段。



### 3\.3 DPO偏好对构建



从单条轨迹中提取DPO训练所需的成对样本：



|字段|来源|角色|
|---|---|---|
|**instruction**|`requirement.description`|任务描述|
|**chosen**|`c1skill_validation.stage_7_final_conclusion`|优选回答（经完整论证）|
|**rejected**|`oracle_analysis.initial_recommendation`|次选回答（初始推荐，尚未经c1skill验证）|



**核心假设**：`c1skill`的7 Stage论证结论在质量上优于Oracle的初始推荐。此假设的验证需通过数据积累后的事后分析确认——若多数案例中两者高度一致或Oracle方案更优，则需调整偏好对的构建策略（如引入人工标注作为chosen/rejected的来源）。



### 3\.4 数据质量控制



|过滤规则|说明|
|---|---|
|LSP校验通过|修改后不引入新增语法/类型错误|
|人工审核通过|用户Review后认可修改方案|
|有效差异存在|Oracle初始推荐与c1skill最终结论存在可识别的差异（非完全一致）|



### 3\.5 数据量预期



|项目|预估|说明|
|---|---|---|
|每月C1级任务量|15\-30条|复杂任务非每日高频发生|
|过滤后有效留存|约50%|LSP校验\+人工审核双重过滤|
|**每月有效数据**|**约10\-15条**||
|建议启动训练门槛|30\-50条|先在7B模型上验证流程|
|建议正式训练门槛|80\-100条|迁移至27B模型|



**说明**：30\-60条数据对于27B模型的DPO训练属于“小样本”范围。建议先用Qwen2\.5\-7B完成流程验证（PoC），确认方法有效后再积累数据扩展至27B。





## 四、微调实施方案



### 4\.1 训练配置



|参数|推荐值|说明|
|---|---|---|
|基础模型|Qwen3\.6\-27B|加载4\-bit量化版本|
|训练方法|DPO|单阶段偏好优化|
|LoRA秩（r）|8\-16|小样本数据用较小的r避免过拟合|
|LoRA Alpha|16\-32|通常为2×r|
|学习率|5e\-6|DPO推荐范围|
|每卡Batch Size|2|双卡共计4|
|梯度累积步数|4|有效Batch Size = 16|
|训练轮数|3\-5|小样本可适当增加|
|最大序列长度|4096|兼顾上下文与显存|
|优化器|paged\_adamw\_8bit|显存优化|



### 4\.2 显存预估



|阶段|单卡显存|说明|
|---|---|---|
|模型加载（4\-bit）|\~14GB|Qwen3\.6\-27B量化后|
|LoRA参数\+优化器|\~4GB|r=16时的估算|
|激活值\+梯度|\~4GB|序列长度4096|
|**总计**|**\~22GB**|符合24GB上限|



### 4\.3 训练命令示例



```Bash
export CUDA_VISIBLE_DEVICES=0,1

python train_dpo.py \
  --model_name Qwen/Qwen3.6-27B \
  --load_in_4bit True \
  --dataset_path ~/train_data/dpo_train.jsonl \
  --output_dir ~/trained_models/lora_weights \
  --num_train_epochs 3 \
  --per_device_train_batch_size 2 \
  --gradient_accumulation_steps 4 \
  --learning_rate 5e-6 \
  --max_seq_length 4096
```



### 4\.4 训练时长预估



- 数据预处理：约10\-15分钟

- 训练（3 Epochs，50条数据）：约60\-90分钟

- 可在午休或晚间空闲时段完成

    

    

## 五、评估与部署策略

### 5\.1 模型评估

|评估维度|方法|通过标准|
|---|---|---|
|**偏好对齐准确率**|在验证集上计算chosen得分 \> rejected得分的比例|\>65%|
|**思辨流程遵循度**|人工检查输出是否包含c1skill风格的论证结构|主观评分≥4/5|
|**代码正确性**|输出方案经LSP校验不引入新增错误|通过率\>90%|
|**通用能力退化**|在标准代码任务上对比微调前后|下降\<5%|

### 5\.2 部署架构（快慢双系统）

|系统|模型|职责|触发条件|
|---|---|---|---|
|**快系统**|微调后的专属模型（Qwen3\.6\-27B \+ LoRA）|快速处理中等复杂度任务，输出自带c1skill风格论证|默认优先调用|
|**慢系统**|DeepSeek V4 API \+ 完整工具链|处理最复杂的C1级问题，保留最高质量|快系统置信度低于阈值，或任务复杂度显着超出|

### 5\.3 回退机制

|机制|说明|
|---|---|
|**模型分流（Feature Flag）**|通过配置开关控制是否使用微调模型，可随时切回API|
|**灰度发布**|先在小范围任务中试用微调模型，验证效果后再扩大范围|
|**一键回滚**|保留基座模型和前一版本权重，发现问题可立即恢复|

## 七、风险与应对



|风险|影响|应对措施|
|---|---|---|
|**核心假设不成立**（Oracle初始推荐与c1skill结论差异小）|DPO训练信号弱|积累足够数据后分析差异分布；若确实差异小，改为人工标注chosen/rejected|
|**数据量不足**|模型无法有效收敛|先在7B上做PoC验证；采用数据增强；降低对首次训练的预期|
|**解析脚本开发困难**|数据采集效率低|初期手动采集，自动化作为长期优化目标|
|**模型遗忘**（通用能力下降）|代码基础能力受损|评估阶段必须包含通用能力测试；设置下降阈值（\<5%）|
|**双卡训练稳定性**|训练中断|启用梯度检查点；定期保存checkpoint；训练前检查散热|





## 八、结语



本报告提出了一条从“推理轨迹”到“专属模型”的完整技术路径：



1. **数据即资产**：每次Sisyphus Ultrawork运行不仅是完成一次任务，更是生产一份可复用的训练样本

2. **方法可蒸馏**：`c1skill`的7 Stage论证方法论可以通过DPO偏好对齐（chosen vs rejected）蒸馏至基座模型

3. **硬件已就绪**：双卡3090在推理依赖API的前提下，可100%投入训练

4. **路径可验证**：通过Qwen2\.5\-7B的PoC先行验证，确认方法论可行后再扩展至27B

    

当前阶段，本方案处于**数据采集初期**。建议先按第一阶段计划启动数据积累，待30条以上数据时启动PoC验证。若PoC效果符合预期，则按路线图继续推进至正式训练。
