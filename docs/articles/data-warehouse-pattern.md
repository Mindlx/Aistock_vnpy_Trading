# 量化交易系统的数据治理：从 API 限流泥潭到统一数据服务层

> 适合读者：量化交易开发者、后端架构师、数据工程师
> 关键词：API 限流、数据缓存、令牌桶、系统架构、零侵入改造
> 写作日期：2026-06-16

---

## 一、问题的起点

### 1.1 三个系统，各自为战

假设你搭建了一个量化交易平台，由三个子系统组成：

- **系统 A**：量化信号系统，每天从新浪财经拉取 K 线数据，训练模型、生成信号
- **系统 B**：AI 分析系统，通过 akshare 库从东方财富获取行情 + 财务数据，用 LLM 做推理
- **系统 C**：多智能体辩论系统，每次运行拉取 8 种数据（行情 + 财务 + 资金流 + 新闻），让多个 AI Agent 辩论后给出评级

三个系统各有各的调度频率：

```
系统 A: 每天15:15 运行一次
系统 B: 每天 10:00 / 11:00 / 14:00 / 15:00 各运行一次 + 事件监控每5分钟
系统 C: 每天 09:31 / 13:00 各运行一次（每次拉取约80次 API）
```

看起来各自独立、职责清晰。但当我们开始监控 API 调用时，发现了一个惊人的事实。

### 1.2 数据重复获取的惊人浪费

三个系统都依赖的同一批数据——股票日 K 线（OHLCV），被重复获取了无数次：

```
系统 A: 每天1次 × 10只股票 = 10次 API 调用
系统 B: 每天4次 × 10只股票 = 40次 API 调用  
系统 C: 每天2次 × 10只股票 = 80次 API 调用（每次含8种数据）
```

**同一只股票的同一天 K 线，三个系统各拉一次，各缓存在各自的数据库里。**

这还不是最严重的。真正的问题在某个特定的时间窗口。

### 1.3 13:00 的「API 海啸」

我们用 systemd 定时器管理所有服务。当查看调度表时，发现了一个可怕的窗口：

```
13:00 ── 系统 C 启动：~80次 akshare 调用（8种数据 × 10只股票）
13:00 ── 系统 B 事件监控启动：~30次 API 调用
        ──────────────────────────────────
        合计：~110次 API 调用 / 5分钟内
```

110 次请求，全部指向**东方财富**的服务器。而东方财富作为免费数据源，对单个 IP 的连续请求非常敏感——社区报告显示约 200 次请求就可能导致 IP 被封禁 5~24 小时。

更糟的是：**三个系统彼此不知道对方也在调用**。系统 C 在被封的边缘疯狂试探时，系统 B 还在傻傻地继续撞墙。

造成了一个什么局面呢？——每天的某个时段，数据获取大面积失败，日志里充斥着 `RemoteDisconnected: Remote end closed connection without response`。

这不是某个代码 bug，这是**架构问题**。

## 二、为什么这个问题不容易被发现

在开始优化之前，我们做了一个详细的诊断。

### 2.1 每个系统都觉得自己的限流没问题

单独看每个系统：

- 系统 A：3 次重试 + 线性退避（1×3s → 2×3s → 3×3s）
- 系统 B：2~5 秒随机延迟 + 指数退避重试 + 断路器模式
- 系统 C：自带重试机制

每个系统单独运行时都工作正常。**问题出在它们同时运行时。**

### 2.2 常见的「修复」误区

很多人会这样修：

- "把系统 C 从 13:00 改到 13:15"——但系统 B 每 5 分钟触发一次事件监控，13:03、13:08、13:13……无论怎么偏移，总会重叠
- "加大重试间隔"——但这只是让问题发生得更慢，而不是不发生
- "给每个系统加更严格的限流"——但限流是 per-process 的，系统 C 限流了，系统 B 不知道，还是继续撞

**这些都是在治疗症状，而不是根因。**

### 2.3 根因分析

使用结构化审阅方法论（我们内部称为 c1skill），逐层深入后发现：

**第一层**（现象）：API 调用频繁失败
**第二层**（直接原因）：同一时间窗口内多个系统同时调同一 API
**第三层**（根因）：没有统一的数据管理层——每个系统各自管理自己的数据获取、缓存、限流和重试

用一句话概括：**三套缓存、三套限流、三套重试策略，管理同一份数据。**

## 三、解决方案的演进

### 3.1 方案 A：修修补补（不推荐）

最简单的方案是调整调度时间、增加随机抖动、减少事件监控频率。但这只是让冲突变得不那么确定，而不是消除冲突。

```
改动: event_monitor 300s → 600s + 随机抖动 30s
效果: API 调用减少 50%，但结构性冲突仍然存在
评价: 治疗症状，不是根因
```

### 3.2 方案 B：中央令牌桶

在系统层加一个跨进程的限流器，所有系统在调 API 前先获取令牌。

```
改动: 实现 SQLite 原子令牌桶 + 修改5+个文件的 API 调用路径
效果: 协调所有 API 调用，但复杂度高
评价: 治标，但没有减少重复调用
```

### 3.3 方案 C：数据服务层（最终采用）

根本性的解决方案是——**在三个系统下面插一层统一的数据服务层。**

```
                   ┌──────────────────┐
                   │   数据仓库调度器    │ (唯一调API者)
                   │  15:30 拉日K线     │
                   │  16:00 拉财务数据  │
                   │  每小时拉新闻      │
                   └────────┬─────────┘
                            │ 写入
                            ▼
                   ┌──────────────────┐
                   │   SQLite 数据湖   │  (统一缓存)
                   ├──────────────────┤
                   │  daily_ohlcv     │
                   │  financial       │
                   │  news_events     │
                   │  capital_flows   │
                   │  fundamentals    │
                   └────────┬─────────┘
                            │ 读取
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
          系统 A         系统 B         系统 C
       (缓存优先读取)  (缓存优先读取)  (缓存优先读取)
```

**核心原则**：每种数据只从外部 API 获取一次，存入统一缓存，所有系统共享。

## 四、关键技术实现

### 4.1 模块设计

最终实现为 8 个文件，约 1300 行 Python 代码：

```
services/data_warehouse/
├── config.py      # 配置中心（TTL、限流参数、股票池）
├── limiter.py     # 跨进程令牌桶限流器
├── storage.py     # SQLite 数据湖（8张表 + CRUD）
├── warehouse.py   # 统一读取接口（WarehouseReader）
├── fetchers.py    # 数据获取器（每种数据类型一个）
├── scheduler.py   # 定时刷新调度器
└── warmer.py      # 首次部署预热脚本
```

### 4.2 跨进程令牌桶：SQLite 原子事务的艺术

既然三个系统运行在不同的进程中，传统的 in-memory 令牌桶就不够用了。我们需要一个**跨进程共享**的限流器。

选择 SQLite 作为共享状态的存储，利用其事务机制实现原子操作：

```python
def consume(self, source, tokens=1.0, timeout=15.0):
    deadline = time.time() + timeout
    while time.time() < deadline:
        conn.execute("BEGIN IMMEDIATE")
        # 1. 读取当前令牌数 + 最后补充时间
        row = conn.execute("SELECT tokens, last_refill, ...")
        # 2. 计算补充后的令牌数
        new_tokens = min(max_t, current + (now - last) * rate)
        if new_tokens >= tokens:
            # 3. CAS 操作：条件 UPDATE
            conn.execute("UPDATE rate_limit_state SET tokens=? "
                         "WHERE source=? AND tokens=?", ...)
            conn.execute("COMMIT")
            return True
        else:
            conn.execute("ROLLBACK")
            time.sleep(min(wait, 0.05))  # 50ms 轮询
    return False  # 超时
```

关键设计点：
- `BEGIN IMMEDIATE` 防止死锁
- `WHERE tokens=current` 是 CAS（Compare-And-Swap），保证原子性
- 50ms 轮询粒度，避免忙等
- 指数退避重试装饰器 `@limiter.retry("source")` 一键保护任何函数

每个 API 源的独立配置：

| API 源 | 速率 | 桶容量 | 重试策略 |
|--------|------|--------|---------|
| 东方财富 | **15 次/分钟** | 15 | 3次指数退避 1s→2s→4s |
| 新浪财经 | 60 次/分钟 | 60 | 3次退避，2s 基础 |
| 腾讯行情 | 120 次/分钟 | 120 | 3次退避，0.5s 基础 |

### 4.3 三阶段读取策略

这是数据服务层的核心——`WarehouseReader` 的读取逻辑：

```
请求数据
  │
  ├─ 缓存命中 + 未过期 ──────→ 直接返回（最快路径，零 API 调用）
  │
  ├─ 缓存存在但已过期 ──────→ 返回旧数据 + stale 标记
  │                           后台异步触发刷新
  │
  └─ 缓存不存在 ────────────→ 降级调用原始 API
                                写入缓存
                                返回
```

每个子系统接入时，只需要在原有数据获取逻辑前加一个 try 块：

```python
def fetch_daily_bars(code, days=120):
    # 数据仓库缓存优先
    try:
        from services.data_warehouse import WarehouseReader
        reader = WarehouseReader()
        if reader.is_fresh(code, "daily_ohlcv"):
            return reader.get_daily_df(code, days=days)
    except ImportError:
        pass  # 仓库不可用 → 走原始 API
    # 以下为原有逻辑（不变）
    ...
```

这就是「零侵入」设计。仓库模块不存在时，`ImportError` 被静默捕获，系统自动回退到原始 API 调用。

### 4.4 多级降级链

当某数据源不可用时，自动降级到备用源：

```python
class DailyFetcher:
    FETCHERS = ["akshare_em", "akshare_sina", "efinance"]

    def fetch(self, code, days=365):
        for name in self.FETCHERS:
            method = getattr(self, f"fetch_{name}")
            try:
                rows = method(code, days)
                if rows:
                    return rows
            except Exception:
                time.sleep(2)  # 源切换间隔
        return []  # 所有源都失败
```

每个方法受令牌桶保护：
```python
@_get_limiter().retry("eastmoney")
def fetch_akshare_em(self, code, days):
    ...
```

### 4.5 SQLite 数据湖

为什么选择 SQLite？对于 10 只股票的规模，SQLite 足够胜任，且零运维成本。

WAL（Write-Ahead Logging）模式允许多个进程同时读取，一个进程写入时不阻塞读取：

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA busy_timeout=5000;
```

8 张业务表 + 2 张元数据表：

| 表 | 主键 | 用途 | TTL |
|----|------|------|-----|
| daily_ohlcv | (code, date) | 日 K 线 | 24h |
| realtime_quotes | (code) | 实时行情 | 5min |
| financial_indicators | (code, period, name) | 财务指标 | 24h |
| capital_flows | (code, date) | 资金流向 | 24h |
| news_events | (id) | 新闻/公告 | 1h |
| fundamentals | (code) | 基本面 | 7d |
| cache_meta | (code, type) | 缓存追踪 | — |
| rate_limit_state | (source) | 令牌桶状态 | — |

## 五、实施策略：分阶段渐进式迁移

架构改造最大的风险是「大爆炸式上线」——把所有改动一次性推到生产环境，出了问题回退困难。

我们采用 6 阶段渐进式迁移，每阶段独立可验证、可回退：

```
Phase 0: 基础建设（3天）
  ├─ 完成：数据仓库模块全部 8 个文件
  ├─ 验证：模块导入成功、令牌桶运行正常、数据库表创建
  └─ 回退：不影响任何系统，直接删除目录即可

Phase 1-3: 子系统接入（4.5天，可并行）
  ├─ 每个系统的改动量：15~35 行代码
  ├─ 零侵入：try/except ImportError 保护
  └─ 验证：缓存命中率、API 调用量对比

Phase 4: 守护进程上线（1.5天）
  ├─ systemd 服务 + 开机自启
  ├─ 定时刷新所有数据类型
  └─ 回退：systemctl stop 即可

Phase 5: 事件链路打通（1天）
  ├─ 事件监控 → 数据湖 → 其他系统直接读取
  └─ 消除重复的新闻/公告请求
```

**关键经验**：每阶段的改动都是**纯增量**。不删除、不改写任何原有逻辑。如果新方案有问题，老方案完好无损。

## 六、效果与收益

### 6.1 量化数据

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 日 K 线 API 调用 | 每天 ~50 次 | 每天 **1 次** | **减 98%** |
| 峰值调用 (13:00) | ~110 次/5min | ~30 次/5min | **减 73%** |
| 东方财富封 IP 概率 | 高 | 极低 | 大幅降低 |
| 数据一致性 | 三份各自缓存 | 一份统一数据 | 保证一致 |

### 6.2 非量化收益

- **可观测性**：所有数据调用从统一入口经过，可以通过 `limiter.stats()` 查看各源的令牌消耗情况
- **可扩展性**：新增子系统只需要一行 `WarehouseReader.get_*()` 即可获得所有数据，不需要处理 API 限流
- **可维护性**：限流参数、TTL 配置集中在 `config.py` 一个文件中，不需要在 5+ 个文件中找重试逻辑
- **零侵入**：每个子系统对数据仓库的依赖是可选的。仓库离线，系统照常运行

## 七、经验与教训

### 7.1 什么是真正的「专业方案」

在讨论方案时，我们发现自己容易陷入「什么是专业」的争论。例如，是 systemd timer 模式专业，还是常驻 daemon 模式专业？

我们用结构化审阅方法（c1skill）论证后发现：**在单机场景下，两种模式在功能、可观测性、可靠性上没有实质差异。** 争论「哪个更专业」是审美偏好，不是技术决策。

真正的问题不是 daemon vs timer，而是**缓存为空**。

### 7.2 不要过早优化调度

我们一度想优化 systemd timer 的调度粒度、把 daemon 拆成 6 个独立 timer。c1skill 论证的结论是：

> 维持当前 daemon 模式完全合理。项目已有 3 个类似模式的 daemon 服务。零改造成本，零功能差异。

**重要的不是你用 daemon 还是 timer，而是你有没有统一的数据管理层。**

### 7.3 东方财富的「反爬军备竞赛」

在实施过程中，我们发现东方财富在 2025~2026 年大幅加强了反爬机制。即使加了严格的 15 次/分钟限流和 3 秒延迟，首次预热时还是立即触发了 `RemoteDisconnected`。

我们的应对策略是**利用多个数据源**：
- 东方财富被禁 → 自动降级到 Sina 财经接口
- Sina 接口的数据维度少一些，但胜在稳定
- 资金流等只有东方财富有的数据，在凌晨低峰期获取

**对于量化交易系统，多数据源降级能力比单一数据源的稳定性更重要。**

### 7.4 架构债务是逐渐累积的

三个系统最初是独立开发的，每个系统都有自己的数据获取逻辑。在各自开发时，这些设计都是合理的。但当它们被集成到一个平台时，**重复的数据获取、各自的限流策略、不共享的缓存**这些架构债务就暴露出来了。

有意思的是：在发现问题之前，我们一直觉得系统运行得挺好。**架构债务在没有触发阈值前，是不可见的。**

---

## 八、总结

量化交易系统的数据治理，核心是三个问题：

1. **数据该谁管？** ——统一管，不要各自为战
2. **数据怎么存？** ——统一缓存，一份数据共享
3. **API 怎么调？** ——统一限流，全局协调

数据服务层模式的核心价值不在于某个具体的技术实现（SQLite、令牌桶、systemd），而在于**它改变了数据在系统中的流动方式**——从各自获取、各自缓存、各自限流，到统一获取、统一缓存、统一限流。

这个模式适用于任何有多个子系统且依赖相同外部数据源的场景，不限于量化交易。
