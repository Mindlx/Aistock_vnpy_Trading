## P0 — 严重 (情报采集链路失效)

### P0-1: SearXNG 自建实例全维度返回 0 条 (情报源实质失效)

- **现象**: 整点分析 16 只股票, 每只 6 维度检索 (最新消息/公告/机构分析/风险排查/业绩/行业), **SearXNG 全部返回 0 条**
- **证据** (log: 当日 256 处):
  ```
  [SearXNG] 搜索 '古麒绒材 001390 股票 最新消息' 成功，实例=http://localhost:8081，返回 0 条结果
  [SearXNG] 搜索 '古麒绒材 研报 目标价 评级 深度分析' 成功，实例=http://localhost:8081，返回 0 条结果
  ```
- **影响**: 整点分析"📢 最新动态"全部显示"新闻搜索返回0条", 情报块实际靠技术面/资金面数据填充, **情报检索链路实质失效**
- **排查建议**:
  1. 检查 SearXNG 服务 (localhost:8081) 是否存活, 配置了哪些引擎
  2. 验证 SearXNG 能否返回中文财经结果 (可能引擎配置缺失/被墙)
  3. 检查 `_filter_news_response` 日期过滤是否过严 (profile=ultra_short, 只留1天)

### P0-2: search_comprehensive_intel 报 NoneType 错误 (综合情报接口崩溃)

- **现象**: Agent 调用 `search_comprehensive_intel` 工具时, 抛 `'NoneType' object has no attribute 'provider'`
- **证据** (log: 当日 32 处):
  ```
  Tool 'search_comprehensive_intel' failed: 'NoneType' object has no attribute 'provider'
  ```
- **影响**: 6 维度综合情报检索接口崩溃, Agent 只能靠单维度 search_stock_news
- **根因方向**: `format_intel_report` 或维度响应处理中, 某 `SearchResponse` 为 None (可能某引擎返回 None 未判空)
- **排查建议**: 检查 `search_service.py:3296` search_comprehensive_intel 各维度 response 的判空逻辑

## P1 — 高 (推送质量)

### P1-1: 东财新闻接口正则 `\u` 无效转义异常

- **现象**: 东财新闻获取反复抛 `Invalid regular expression: invalid escape sequence: \u`
- **证据** (log: 当日 176 处):
  ```
  [EastMoney] 东方财富新闻获取失败: Invalid regular expression: invalid escape sequence: \u
  ```
- **影响**: 东财个股新闻源大面积失败, 依赖此源的公告/新闻采集静默降级
- **根因方向**: 正则模式中裸 `\u` (应写 `\\u` 或原始字符串)
- **排查建议**: 定位 `search_service.py` 中带 `\u` 的正则, 改为 `r"\u"` 原始字符串

### P1-2: 推送文本 HTML `<em>` 标签残留

- **现象**: 盘前情报推送标题含 `<em>` 标签 (来自东财搜索 API 的 preTag/postTag 未清理)
- **证据** (log: 当日 9 处):
  ```
  每日情报 盘前 [公告8]: <em>雷迪克</em>：关于公司实际控制人增持股份计划的公告
  每日情报 盘前 [公告9]: <em>*ST起步</em>：<em>*ST起步</em>：...
  ```
- **影响**: 企业微信 markdown 渲染残留 HTML 标记, 推送可读性差
- **根因方向**: `_push_highlights` 清洗逻辑 (main.py:510) 未覆盖 `_fetch_breakfast_finance`/个股新闻路径
- **排查建议**: 统一在入库/推送前清洗 `<em>` (参考 mlaistock clean_text)

### P1-3: 盘前情报 4182 字符超限分批 (推送体验)

- **现象**: 盘前情报 44 条推送 4182 字符 (6152 字节), 超企业微信 markdown 上限, 触发分批
- **证据** (log):
  ```
  消息内容超长(6152字节/4182字符)，将分批发送
  ```
- **影响**: 单条推送被拆成多条, 用户阅读碎片化
- **排查建议**: 参考 mlaistock 的"限15条+摘要"策略, 高重要情报精简为 top N

## P3 — 低 (时效优化)

### P3-1: 复盘推送 20:30 时效滞后

- **现象**: 大盘复盘 (全天) 在 20:30 推送, 但 15:45 收盘后数据已完整
- **证据**: 旧系统 15:45 全天复盘成功 (PDF 正常生成); 20:30 推送滞后约 5 小时
- **影响**: 用户盘后决策时效性差 (晚间才看到复盘)
- **建议**: 复盘提前到 16:00 左右 (收盘后 1 小时内), 与整点分析/数据抓取错开
  - ⚠️ 注意: 需确保当日数据已落库 (mlaistock 实证: 15:35 时 tushare 当日数据未发布, 会滞后一天; 建议 16:30 数据抓取后)

### P3-2: 复盘使用"昨日数据"的滞后陷阱 (风险警示)

> 本系统当前未触发 (复盘数据源为实时 API), 但这是**同一类滞后 bug 的高危风险点**, 团队改动数据源时必须警惕。

- **现象**: 复盘报告使用昨日数据生成 (指数/涨跌/涨停为昨日), 报告日期却是当日 — **静默滞后, 无告警**
- **场景**: 复盘的涨跌家数/涨停池/指数K线若改为从**数据湖日K表**读取 (而非实时 API), 当日数据需在收盘后另行抓取落库; 若复盘早于落库时刻运行 → 读到昨日
  - 实测: mlaistock 新系统 15:35 复盘时 market.db daily_ohlcv 未落当日数据 (16:30 才抓取) → 复盘 data_date=昨日, 滞后一天无任何报错
- **当前状态**: 旧系统 2026-08-12 15:45 复盘实测为当日数据 (涨:4128 跌:1279 涨停:91 成交:21666亿 = 当日收盘), **未受影响** — 因为指数/涨跌/涨停均走实时 API (efinance get_realtime_quotes / akshare stock_zt_pool_em)
- **修复建议** (若未来引入数据湖缓存):
  1. 复盘读取涨跌家数/涨停前, 先校验 `MAX(date)` 是否为当日, 非当日则告警/回退实时源
  2. 复盘调度时刻必须晚于日K落库任务 (mlaistock 最终定为 16:40, 16:30 落库之后)
  3. 参考本系统已有的 `_check_fusion_freshness` 模式 (融合文件新鲜度校验 + 报告内标注告警)
