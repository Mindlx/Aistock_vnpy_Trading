Execute c1skill — 交叉层问题审计与修复方法论。

对多层系统中发现的任何问题，执行从原架构理解 → 跨学科著作证据论证 → 修复 → 验证的完整闭环。

## 核心教训（必读）

**两个致命缺陷必须避免：**
1. 在理解原架构前就定义问题 — 先 Stage 0
2. 证据搜集允许论文作为来源 — 著作 ONLY

## 证据等级体系

| 等级 | 来源 | 何时使用 |
|:----:|:-----|:---------|
| L1 | 权威著作（教材、专著） | 所有理论论证的唯一来源 |
| L2 | 本系统代码 + 设计文档 | 原架构意图、实际数据流 |
| L3 | 行业实践（方法论著作） | 补充实践框架 |

禁止：学术论文、博客、AI生成内容

## 方法论：8 阶段闭环

### Stage 0 — 原架构深入分析（最重要）

1. 阅读原始设计文档、README、代码 docstring
2. 阅读相关源代码中的设计意图
3. 追溯 git 历史
4. 回答：这个设计是为解决什么问题？刻意还是偶然积累？

产出：原架构设计意图摘要 + "刻意 vs 偶然"判定

### Stage 1 — 精确定义问题

前提：Stage 0 已完成。区分"确实有问题" vs "原设计如此"。
标注严重程度 CRITICAL / HIGH / MEDIUM / LOW，明确影响范围。

### Stage 2 — 跨学科著作证据搜集（并行，著作 ONLY）

同时启动 3-5 个搜索路径，每个覆盖一个学科领域。
搜索目标：著作中与当前问题相关的具体论述、定理、框架。
关键：寻找独立收敛——多个领域用不同方法论指向同一结论。

标准学科矩阵：
- 统计学习理论：Hastie ESL, Bishop PRML
- 量化组合管理：Grinold & Kahn APM
- 量化 ML：López de Prado AFML
- 行为/认知科学：Kahneman TFS, Taleb Black Swan
- 因果/认识论：Pearl Book of Why

### Stage 3 — 跨学科综合

按支持/反对分类，统计各领域判决方向。
独立收敛 > 互相引用。产出判决矩阵。

### Stage 4 — 主动寻找反方论据（不可跳过）

假设原论述错误，主动寻找支持反方的著作证据。
量化反方正确范围。如反方部分成立，修正原论述精度。

### Stage 5 — 修复方案设计

原则：不删功能、校准>消除、零风险优先、经验测量优先。
分级：Phase 1 零风险 → Phase 2 诊断脚本 → Phase 3 逻辑改动

### Stage 6 — 实施与验证

实施修复 → 编译检查 → 运行端到端测试 → 检查输出不劣化
产出：commit + 验证记录 + 假设vs实际对照

### Stage 7 — 自我批判

回到 Stage 0，判断修复是增强还是违背架构初衷。
如果会削弱刻意设计且有科学依据的设计 — 不要修复。

## 关键规则

1. Stage 0 不可跳过
2. 著作 ONLY，禁止论文
3. 永远并行搜索
4. 寻找独立收敛
5. 主动找反方（Stage 4 不是可选的）
6. 先测量再改逻辑
7. 修复后验证不劣化
8. 留痕：每个 Stage 产出必须写入文档
